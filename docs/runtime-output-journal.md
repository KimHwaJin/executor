# Runtime Output Journal

Status: implementation contract for PR-004; thresholds pending T35 evidence.

## Purpose

Executor currently collects every Jupyter output in one in-process list, duplicates that list in
PostgreSQL Step and Step Attempt rows, and rewrites a complete notebook from those rows. This is
correct for small outputs but makes Executor memory and PostgreSQL growth proportional to the full
cell output multiplied by concurrent executions.

The replacement keeps complete output on Runtime-owned storage while Executor retains bounded
metadata, summaries, previews, and stable references. It is a Runtime-neutral domain contract:
Jupyter is the first provider, but the application layer does not expose kernels, cells, or
Jupyter Contents API types.

This document does not select byte ceilings. T35 measurements select those values from deployed
Executor and Runtime limits.

## Ownership boundary

- The Runtime owns complete output bytes, journals, and the completed notebook.
- Executor owns execution state, output metadata, ordering, lineage, and public result references.
- PostgreSQL is the source of truth for whether an output belongs to the current fenced execution
  attempt. Runtime files cannot make a stale Worker authoritative.
- Redis contains bounded summaries and references only. Full text, HTML, JSON, or base64 image
  bodies are not integration-event fields.
- Agent reads small previews from normal result contracts and retrieves referenced content only
  when needed. Executor never exposes Runtime credentials or a raw privileged Contents URL.

## Runtime-neutral port

The application and Worker depend on an `OutputJournal` port with these operations:

1. `begin`: create or reopen one journal for a Step execution.
2. `append`: append an ordered, idempotent batch and return the committed offset.
3. `finalize`: atomically close the journal and return its immutable descriptor and summary.
4. `abort`: mark an incomplete journal without deleting already committed output.
5. `list`: page through output descriptors without loading content bodies.
6. `read`: stream one referenced representation or a requested byte range.
7. `materialize_notebook`: atomically construct the complete notebook from finalized journals.

The Jupyter driver maps this port to authenticated extension endpoints under
`/executor/storage/output-journals`. Another Runtime provider may implement the same port without
notebooks or Jupyter message types.

## Journal identity and fencing

One journal is uniquely identified by:

- `execution_id`;
- `operation_id`;
- `step_id` and sequence;
- `execution_attempt_id`;
- execution lease `fencing_token`;
- Runtime Target and Runtime session identity.

The attempt and fencing token are part of the storage identity, not just mutable metadata. A stale
Worker therefore writes to an old journal and cannot append to or finalize the journal selected by
the current PostgreSQL fence. Executor checks its active lease before every durable metadata or
event write.

`append` uses an expected committed offset and a stable batch ID. Replaying the same batch returns
the original offset; using the same batch ID with different content fails. A gap or conflicting
offset fails without modifying the journal.

## Runtime storage layout

The Jupyter provider uses safe relative paths under the existing execution workspace:

```text
<workspace>/
├── notebooks/
│   └── execution.ipynb
└── outputs/
    └── <operation-id>/<step-id>/<attempt-id>/<fencing-token>/
        ├── journal.json
        ├── source.py
        ├── batches/
        │   └── <batch-id>.json
        └── content/
            └── <output-id>/<representation-id>.bin
```

- `journal.json` is a small state document written through temporary-file plus atomic rename.
- `source.py` stores the exact Step source once when the Journal begins; notebook
  materialization therefore does not resend all prior cell sources.
- `batches/` contains immutable, idempotent append segments with ordered output metadata, never an
  unbounded inline body. `journal.json.committed_offset` advances only after the segment is durable;
  opening the journal repairs an interrupted state update from those segments.
- `content/` contains large text and MIME representations as native bytes.
- Small content may remain inline in a record only below the measured inline ceiling.
- Paths are generated by Executor/Runtime adapters and validated by the Jupyter extension. Client
  requests never supply an arbitrary filesystem path.

## Output record

Each immutable record contains at least:

```json
{
  "schema_version": "1.0",
  "output_id": "UUID",
  "ordinal": 3,
  "kind": "STREAM | DISPLAY | RESULT | ERROR",
  "stream_name": "stdout",
  "execution_count": 12,
  "representations": [
    {
      "representation_id": "UUID",
      "media_type": "text/plain",
      "size_bytes": 1234,
      "checksum_sha256": "hex",
      "complete": true,
      "inline_preview": "bounded optional preview",
      "truncated_in_preview": false,
      "content_ref": "opaque stable reference"
    }
  ],
  "metadata": {},
  "created_at": "RFC3339 timestamp"
}
```

Jupyter mapping is deterministic:

- `stream` becomes `STREAM` and retains stdout/stderr.
- `display_data` becomes `DISPLAY` with one representation per MIME key.
- `execute_result` becomes `RESULT` and retains `execution_count`.
- `error` becomes `ERROR`; name, value, and traceback are representations/metadata.
- Jupyter transient display IDs and future update messages remain explicit metadata so a later
  implementation can preserve display-update semantics without changing the public identity.

`complete=false` means Runtime delivery or journal finalization ended before the full body was
committed. `truncated_in_preview=true` only describes the bounded preview; it never claims the
referenced original is truncated.

## Finalization and notebook materialization

When a Step reaches idle or fails:

1. Executor flushes the last bounded append batch.
2. Runtime finalizes the journal and returns output count, total bytes, MIME summary, checksum, and
   immutable journal reference.
3. Executor verifies the current lease fence and stores only that descriptor and bounded preview.
4. Executor publishes the existing Step result event with `output_summary` and `result_ref`.
5. For a successful execution, Runtime materializes `execution.ipynb` from code sources and
   finalized journals using a streaming temporary-file writer and atomic rename. It does not ask
   Executor to load every prior output again.

The notebook remains a normal, complete `.ipynb` file. The journal is an internal durability and
incremental-access structure, not a replacement format visible to users.

If Executor disconnects, already committed records remain recoverable. Reconciliation uses the
PostgreSQL owner and fence to either resume a compatible journal operation or mark it aborted. It
does not replay unknown code merely because a journal exists.

## PostgreSQL projection

PR-004 introduces output metadata rows rather than full output JSON duplication. The logical
projection contains:

- output identity, execution/operation/step/attempt lineage, ordinal and kind;
- completion and preview-truncation flags;
- output and representation byte sizes and checksums;
- MIME types, stream name, execution count, bounded preview, and opaque content references;
- normal audit fields.

Current Step and Step Attempt response models use the same referenced output projection. Their
large `outputs` JSON bodies are removed only in the migration that also enables journal-backed
reads; there is no period where complete output becomes unreachable.

## Public reads

The public transport is additive during implementation:

- output list: cursor-paginated metadata and bounded previews;
- output detail: metadata for one output and its representations;
- output content: streaming native bytes with media type, checksum, content length, and HTTP Range
  support;
- notebook reads: existing notebook metadata/cell reads, implemented without requiring output
  bodies in PostgreSQL.

REST and MCP reuse shared Pydantic metadata contracts. MCP returns small inline content when it is
within the selected threshold; otherwise it returns the same stable reference and tells the Agent
which content operation to call. Large binary bodies use the streaming HTTP content operation
rather than an MCP JSON/base64 envelope.

## Safety bounds selected after T35

The implementation will configure and report separate bounds for:

- one Runtime WebSocket message;
- one Executor append batch and total in-process output buffer;
- inline PostgreSQL/API preview;
- one output-content response or byte range;
- total retained output per Step and Execution as an explicit platform safety ceiling.

Crossing a memory or preview bound switches to journal-backed storage. It does not silently drop
content. Crossing the final platform safety ceiling fails the Step with an explicit output-limit
failure while keeping already committed journal metadata observable.
