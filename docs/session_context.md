# 동일 세션 멀티턴 컨텍스트

같은 `thread_id`로 완료된 그래프를 다시 호출한다. Checkpointer가 State를 복원하며,
프로젝트 공유 Store나 새 DB 테이블은 사용하지 않는다. HITL/Executor 대기 중에는
기존대로 `Command(resume=...)`를 사용한다. 완료된 보고서에 대한 후속 질문은
새 입력으로 `START`에서 시작하여 `analysis_question`에서 답변한 뒤 `END`한다.

## State와 확정 기록

- `messages`: 원문을 삭제하지 않는 기존 누적 이력. UI messages 테이블과 별개다.
- `conversation_summary`: 오래된 대화의 LLM 요약.
- `summarized_through_message_id`: 성공적으로 요약한 마지막 전체 턴의 메시지 ID.
- `current_analysis_task_id`: 현재 참조하는 분석.
- `analysis_records[task_id]`: 원래 요청, 워크플로우 ID/버전, 확정 입력값,
  계획 도구, 실제 결과 상태와 제한된 증거, 보고서 발췌, 한계와 원본 참조.
- `referenced_analysis_task_ids`, `analysis_reference_ambiguous`: 이번 질문의 참조 대상.
- `last_received_message_id`: messages-only 입력과 복원된 user_request를 구분한다.

분석 기록은 후보 선택, 입력 확정, 승인, 제출, 실행 결과 수집, 보고서 완료 노드의
업데이트와 함께 기록한다. LLM이 추정한 파라미터를 확정값으로 저장하지 않는다.
실패/미실행 상태를 그대로 유지하고 계획 목록과 실행 증거를 분리한다.
새 분석을 시작할 때 실행 관련 State를 초기화하되 대화·요약·분석 기록은 유지한다.

보고서 원문은 `messages`에 `report-{task_id}` ID로 보존한다. 후속 응답은 해당
메시지를 조회하여 사용하며, 입력 예산을 초과할 때만 생략 표시를 붙여 줄인다.
`result_summary`는 현재 의미 요약이 아닌 최대 4,000자의 보고서 발췌이며
`summary_kind=report_excerpt`로 표시한다. 한계 제목의 보고서 구간도 별도로 보존한다.
대규모 실행 출력은 문자열/목록/필드 수를 제한하고 생략을 표시한다. 원본 결과는
실행 ID와 기존 산출물 참조로 추적한다. 이 단계에서는 외부 파일/API를 자동으로
재조회하지 않으므로 근거에 없는 세부 사항은 확인할 수 없다고 답하도록 지시한다.

## 입력 구성과 토큰 예산

`ContextBuilder`는 일반 Python 코드다. 노드가 목적을 명시한다. 라우팅은 요약,
최근 대화, 분석 목록을 받고, 후속 질문은 라우터가 선택한 분석 기록과 보고서를 받는다.
여러 분석 비교를 지원하고, 없는 ID 또는 모호한 참조는 확인 질문으로 처리한다.
이전 분석 파라미터를 새 분석에 자동으로 적용하지 않는다.

```dotenv
CONTEXT_INPUT_BUDGET_TOKENS=32000
CONTEXT_SUMMARY_TRIGGER_TOKENS=8000
```

컨텍스트 관련 환경변수는 위 두 개만 사용한다. 모델 한도·출력 예약량·바이트 예산 관련
기존 환경변수는 제거했다. 모델을 바꾸거나 요청의 출력 파라미터를 변경해도 이 두 값은
변하지 않는다. `128 <= 요약 임계값 < 전체 입력 예산`, 전체 입력 예산은 1024 이상이어야 한다.

길이는 프로젝트에 포함한 **tiktoken `cl100k_base` 토크나이저의 토큰 수**로 계산한다.
문자 수나 UTF-8 바이트 수로 환산하지 않는다. 공통 토크나이저이므로 GLM/Qwen 서버의
자체 토크나이저·채팅 템플릿·과금 usage와는 차이가 날 수 있다. 실제 서버별 정확한
토큰 수를 자동 측정하는 기능은 아니다. 동일한 기준으로 모델 전환 전후의 예산을 유지한다.
사전 파일은 패키지에 포함하고 해시를 검증한다. 내부망 실행 시 다운로드하지 않으며,
파일이 없거나 손상되면 오류를 내고 바이트 계산으로 대체하지 않는다.

전체 입력 예산을 `I`, 요약 임계값을 `S`라고 할 때 나머지는 코드에서 계산한다.

| 내부 예산 | 계산 | 기본 설정에서의 토큰 수 |
| --- | --- | ---: |
| 최근 대화 | `min(S // 2, I // 4)` | 4000 |
| 라우팅용 분석 목록 | `I // 16` | 2000 |
| 요약문 목표 상한 | `min(1024, S // 8)` | 1000 |
| 긴 턴의 요약 구간 | `min(S // 4, I // 8)` | 2000 |

위 비율은 **운영자가 정한 공통 입력/요약 예산**에만 적용한다. 모델의 컨텍스트 크기나
출력 한도에 비례하여 계산하지 않는다. `I`는 대화만의 한도가 아니라 시스템 프롬프트,
스키마, 업무 입력, 대화, 분석 근거를 합친 전체 입력 한도다. 각 메모리 예산을 더한 값이
전체 입력 한도를 대체하지 않는다.

실제 LLM 호출 직전에 시스템 프롬프트·출력 스키마·JSON 포장·재시도 피드백을 토큰으로
계산하고, 채팅 포맷 차이를 위한 소량의 고정 여유(요청당 32, 메시지당 32토큰)를 더해 검사한다.
초과하면 참조 ID가 있는 보고서 발췌를 줄인다. 미요약 대화와 기존 요약은 제외하지 않는다.
대화, 확정 파라미터와 필수 스키마를 보존한 채 한도를 맞출 수 없으면 `ContextBudgetExceeded`로 명시적으로 실패한다.
후속 질문 경로에서는 범위를 좁혀 달라는 응답으로 변환한다.

일반 LLM 호출에는 더 이상 환경변수 기반의 출력 상한을 강제로 넣지 않는다.
`agent_config.py`의 `MAIN_MODEL_CONFIG.parameters`에 `max_output_tokens` 또는 `max_tokens`가 있으면 전달하고,
없으면 모델 서버 기본값을 사용한다. 요약 호출만 파생된 요약문 목표를 출력 상한으로
사용하며, 서버 설정에서 더 작은 출력 상한을 지정했다면 그 값을 따른다.
모델의 실제 컨텍스트 용량은 자동 검사하지 않으므로 전체 입력 예산은 가장 작은 모델의
실제 지원 범위와 출력량을 고려하여 설정한다.

환경변수 변경 후 API와 Executor 이벤트 Worker를 모두 재시작한다. 원문과 분석 기록을
삭제하거나 DB를 변경할 필요는 없다. DEBUG 로그에는 계산된 토큰 수·예산·응답 usage·
종료 사유를 남긴다. `finish_reason=length` 응답은 완성된 보고서/요약으로 저장하지 않는다.

## 요약 노드

라우팅 전에 `summarize_conversation`이 실행된다. 사용자 턴이 두 개 이상이고 기존 요약과
미요약 대화의 토큰 수가 `CONTEXT_SUMMARY_TRIGGER_TOKENS`를 초과하면 요약한다.
이 임계값에 도달하지 않아도, 완료된 미요약 턴이 최근 대화 목표 예산을 넘으면
오래된 턴부터 요약하여 나머지 원문이 목표 예산에 들어오도록 한다.
요약문은 파생된 목표 토큰 수 이내로 유지하며, 초과하면 더 짧게 다시 요청한다.
현재 진행 중인 마지막 턴은 유지한다. 직전 완료 턴도 너무 크면 요약하며, 긴 턴은
토큰 예산에 맞춰 여러 구간으로 나눈다.
한글·이모지 문자가 손상되지 않도록 토큰 경계에서 디코딩을 확인한다.
턴 수를 네 개로 제한하지 않고 필요한 오래된 턴들을 처리한다.

한 턴의 모든 구간이 성공해야 요약과 커서를 갱신한다. 실패하면 이전 요약/커서를
유지하고 다음 호출에서 재시도할 수 있다. 아직 요약되지 않은 원문은 목표 예산을
초과해도 입력에 유지한다. 전체 입력 한도를 넘으면 대화를 제외하지 않고 명시적으로
실패한다. 원문은 언제나 유지한다. 도구 호출과 응답은 전체 사용자 턴 단위로 선택한다.

## API 저장과 검증

API invoke/stream은 실행 전 체크포인트의 메시지 개수부터 새 메시지만 저장한다.
복원된 노트북·실행 제출 응답을 새 호출의 산출물로 다시 기록하지 않고, 읽기 전용
후속 질문을 이전 분석 작업 ID에 새 작업처럼 연결하지 않는다.

`test_session_context`는 체크포인트 기반 END→START, HITL→실행→보고서→후속 질문,
여러 분석 비교, 세션 격리, 입력 예산, 요약 실패, API 저장 delta를 외부 모델 없이 검증한다.
실제 모델의 라우팅·요약·답변 품질과 실제 Postgres 연결은 별도 통합 검증 대상이다.
